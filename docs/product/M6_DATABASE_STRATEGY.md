## New tables

### ai_provider_config (configuration metadata — no secrets)

**Important**: Do NOT hand-write `0004_ai_provider.sql`. Run `pnpm drizzle-kit generate` after adding the Drizzle schema additions below. This generates the SQL AND updates `src/database/migrations/meta/_journal.json` atomically. If the journal is not updated, the migration silently skips on startup (no error). The generated SQL will use backtick-quoted identifiers matching the 0000–0003 format.

```sql
-- src/database/migrations/0004_ai_provider.sql
-- Generated by pnpm drizzle-kit generate — do not edit by hand

CREATE TABLE IF NOT EXISTS `ai_provider_config` (
  `id` text PRIMARY KEY DEFAULT 'default' NOT NULL,
  `provider_type` text DEFAULT 'openai_compatible' NOT NULL,
  `base_url` text DEFAULT 'https://api.openai.com' NOT NULL,
  `model` text DEFAULT 'gpt-4o-mini' NOT NULL,
  `is_configured` integer DEFAULT 0 NOT NULL,
  `consent_recorded_at` integer,
  `last_test_status` text,
  `last_test_at` integer,
  `created_at` integer NOT NULL DEFAULT (unixepoch() * 1000),
  `updated_at` integer NOT NULL DEFAULT (unixepoch() * 1000)
);

CREATE TABLE IF NOT EXISTS `ai_secrets` (
  `id` text PRIMARY KEY DEFAULT 'ai_provider' NOT NULL,
  `encrypted_key` blob,
  `updated_at` integer NOT NULL DEFAULT (unixepoch() * 1000)
);
```

Note: `created_at` has `DEFAULT (unixepoch() * 1000)` so INSERT is safe if called before `ensureAiProviderConfigRow`. However, `updateAiProviderConfig` is the preferred method after initialization (see DatabaseService additions below).

CHECK constraints:
- `is_configured IN (0, 1)` added via Drizzle `.check()` or raw SQL
- `provider_type` check deferred — only `'openai_compatible'` valid in M6; add CHECK in M7 when more providers exist

Both tables use singleton rows (id = `'default'` or `'ai_provider'`). This mirrors the existing `app_settings` singleton pattern.

### No ai_request_log in M6

Request history is deferred to M7 or a later milestone. Rationale:
- M6's only AI call is the connection test. Logging connection test history has low value.
- M7 may choose to persist candidate generation request metadata.
- Adding the table now (before M7 defines the schema) creates risk of schema churn.

M7 will add `ai_request_log` with `0005_ai_request_log.sql`.

## DatabaseService additions

```typescript
// Methods added to DatabaseService

public getAiProviderConfig(): AiProviderConfigRecord;
// UPDATE-only: assumes ensureAiProviderConfigRow() was called during initialize()
// Named "update" not "upsert" to avoid implying INSERT safety before init
public updateAiProviderConfig(input: Partial<AiProviderConfigInput>): AiProviderConfigRecord;
public getAiSecretBlob(): Buffer | null;
public setAiSecretBlob(blob: Buffer): void;
public clearAiSecretBlob(): void;
```

`getAiProviderConfig()` initializes the default row if not present (same pattern as `ensureDefaultSettings()`).

Note: Drizzle ORM does not support native `INSERT OR REPLACE` / `ON CONFLICT DO UPDATE` — use raw `db.prepare()` for upsert patterns as existing code does in `upsertSubtitleDocument`. Since `updateAiProviderConfig` is UPDATE-only after init, raw `db.prepare()` is used for the update queries to remain consistent with existing patterns.

`getAiSecretBlob()` returns the raw encrypted Buffer or null. Only `AiSecretsService` calls this.

## Persistence rules

| Data | Persisted | When |
|---|---|---|
| Provider type, base URL, model | YES | On `setApiKey` or when user changes settings |
| `is_configured` flag | YES | Set true on successful key store, false on clear |
| `consent_recorded_at` | YES | On user clicking "I understand" |
| `last_test_status` | YES | On test completion (success or failure code) |
| `last_test_at` | YES | On test completion |
| Encrypted API key blob | YES | In `ai_secrets.encrypted_key` as BLOB |
| Raw API key | NEVER | Not stored anywhere |
| Request text / prompt content | NEVER | |
| Response content | NEVER | |
| Usage token counts | DEFERRED | M7 decision |

## Restart behavior

On `DatabaseService.initialize()`:
1. `ensureAiProviderConfigRow()` — inserts default row if missing.
2. `ensureAiSecretsRow()` — inserts empty row (null blob) if missing.

On `AiConfigurationService.initialize()` (called after db init):
1. Reads `ai_provider_config` row.
2. Checks `ai_secrets.encrypted_key IS NOT NULL`.
3. Checks `safeStorage.isEncryptionAvailable()`.
4. Sets in-memory `configurationStatus` accordingly.
5. Sets in-memory `consentRecorded` flag.

Status `testing`, `available`, `unavailable`, `invalid_configuration`, `rate_limited`, `offline` are never persisted directly as the status field. They are derived from `is_configured` + `last_test_status` + `last_test_at` on each read.

## Migration safety

`0004_ai_provider.sql` uses `CREATE TABLE IF NOT EXISTS`. Safe to run on existing databases. No data loss. No column drops. Compatible with existing M1–M5 migrations.

## Transaction policy

`setApiKey` operation (atomic):
```
BEGIN
  update ai_provider_config SET providerType, baseUrl, model, isConfigured=1,
    lastTestStatus=NULL, lastTestAt=NULL, updatedAt  -- stale test status cleared
  update ai_secrets SET encryptedKey=blob, updatedAt
COMMIT
```

**Important**: `lastTestStatus` and `lastTestAt` must be reset to NULL when the key changes. A user replacing their key with a new one must not inherit a stale "Connected" status from a previous test.

`clearConfiguration` operation (atomic):
```
BEGIN
  update ai_provider_config (isConfigured=0, consentRecordedAt=NULL, lastTestStatus=NULL, lastTestAt=NULL, updatedAt)
  update ai_secrets (encryptedKey=NULL, updatedAt)
COMMIT
```

Transactions ensure the metadata and secret blob are always consistent.

## Test requirements

`tests/main/aiConfiguration.test.ts`:
1. `getAiProviderConfig()` returns default row after initialization
2. `upsertAiProviderConfig({model: 'gpt-4o'})` updates model field
3. `setAiSecretBlob(buf)` persists blob, `getAiSecretBlob()` returns same buffer
4. `clearAiSecretBlob()` sets encrypted_key to NULL
5. `setApiKey` + `clearConfiguration` operate atomically (both tables consistent)
6. Restart persistence: initialize, set key, close, re-initialize, verify isConfigured=true and blob present
7. `consentRecordedAt` persists and clears correctly
8. No raw key string ever returned from any DatabaseService method
